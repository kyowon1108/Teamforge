# TeamForge 구현 우선순위 정리

## 전제
- **Kakao 연동은 제외**
- 현재 구현 상태는 **인증 / 팀 생성 / 초대 / 역할 분기 / 설문 / 결과 / 팀 대시보드**까지 안정적으로 연결된 상태
- 다음 목표는 **좋은 onboarding product**에서 **계속 돌아오는 운영 product**로 넘어가는 것
- 우선순위 기준:
  1. 지금 있는 MVP를 실제로 더 잘 쓰게 만드는가
  2. 다음 단계인 retention loop로 자연스럽게 이어지는가
  3. 구현 난이도 대비 효과가 큰가

---

| 우선순위 | 작업 | 핵심 목적 |
|---|---|---|
| 1 | Meeting hub 최소 버전 | 주간 재방문 이유 만들기 |

# 1. Meeting hub 최소 버전

## 목적
현재 제품의 가장 큰 약점은 **설문과 결과 이후 다시 돌아올 이유가 약하다는 점**이다.  
Meeting hub를 붙이면 사용자는 아래 이유로 다시 들어오게 된다.

- 회의 후 요약 확인
- 액션 아이템 확인
- 다음 회의 안건 확인

즉, **첫 번째 retention loop**를 만드는 기능이다.

## 최소 구현 범위
| 기능 | 최소 구현 |
|---|---|
| 회의 입력 | 텍스트 붙여넣기 |
| AI 요약 | 핵심 논의 3~5줄 |
| 액션 아이템 추출 | 누가 / 무엇을 / 언제까지 |
| 액션 상태 | open / done 토글 |
| 회의 히스토리 | 최신순 리스트 |
| 다음 안건 생성 | 미완료 액션 기준 자동 생성 |

## 지금 당장 필요한 것
- 회의 1개 저장 가능
- 저장 후 AI 분석 성공 / 실패 상태 명확히 표시
- 액션 아이템 완료 체크 가능
- 이전 회의를 다시 열어볼 수 있음

## 나중으로 미뤄도 되는 것
- Slack import
- Notion import
- Zoom / Meet auto-import
- 음성 STT
- Drift 분석
- 고급 안건 생성

## 완료 기준
- Leader / Member가 회의록 1개를 올릴 수 있다
- AI 요약과 액션 아이템이 생성된다
- 액션을 완료 처리하면 다음 안건에 반영된다
- 팀 단위로 회의 히스토리가 누적된다

# 2. 팀 대시보드 액션 허브화

## 목적
현재 팀 대시보드는 정보 제공은 잘하지만, 아직은 **보는 화면**에 가깝다.  
이를 **팀장이 바로 행동할 수 있는 화면**으로 바꿔야 한다.

## 왜 중요한가
- 현재 제품에서 가장 중요한 유저는 **팀장**
- 팀장이 제품을 밀어주지 않으면 팀원도 계속 사용하지 않음
- 따라서 대시보드는 단순 리포트가 아니라 **다음 행동 시작점**이어야 함

## 추가해야 할 액션
| 영역 | 추가 액션 |
|---|---|
| 설문 진행률 | 미완료자 리마인드 보내기 |
| 역할 제안 | 역할 확정하기 |
| 스킬 분석 | 주제 결정 시작하기 |
| 팀원 목록 | Git 레벨 낮은 팀원에게 온보딩 추천 |
| 팀 준비 상태 | 킥오프 준비 시작 CTA |

## 추천 UI 구조
상단에 **현재 해야 할 일** 카드 추가

예시:
1. 설문 미완료 2명 → 리마인드 보내기
2. 역할 제안 미확정 → 역할 확정하기
3. 주제 미정 → 주제 결정 시작하기

## 완료 기준
- 팀장이 대시보드에서 다음 행동 3개를 바로 볼 수 있다
- 클릭 한 번으로 리마인드 / 역할 확정 / 다음 단계 진입이 가능하다
- 대시보드가 “분석 결과”보다 “진행 단계” 중심으로 보인다

# 3. AI 결과 설명 가능성 강화

## 목적
현재 결과는 잘 나오더라도, 사용자 입장에서는 **왜 그렇게 나왔는지**가 중요하다.  
추천 역할과 점수가 납득되어야 신뢰도가 생긴다.

## 추가해야 할 설명
### 개인 결과 페이지
| 항목 | 설명 예시 |
|---|---|
| 추천 역할 | 백엔드/DB 점수가 높고, 최근 프로젝트에서 API/DB 경험이 확인되어 백엔드 역할이 추천되었습니다. |
| 강점 | React, Next.js 숙련도와 Top Strengths 응답이 일치합니다. |
| 보강 필요 | DevOps 관련 기술 선택이 적어 배포/인프라 역할은 보조 수준이 적합합니다. |

### 팀 대시보드 역할 제안
| 항목 | 설명 예시 |
|---|---|
| 역할 후보 | 희망 역할과 실제 경험이 일치하고, 팀 내 해당 스킬 점수가 가장 높습니다. |
| 보조 후보 | 희망 역할은 아니지만 기술 점수상 대체 가능성이 높습니다. |

## 구현 포인트
- 기존 계산값을 그대로 활용
- 설명은 템플릿 기반으로 먼저 구현 가능
- 추후 AI generated explanation으로 확장 가능

## 완료 기준
- 추천 역할에 1~2문장 근거가 붙는다
- 팀장이 역할 배정 결과를 납득할 수 있다
- 결과 페이지 신뢰도가 올라간다

# 4. 점수 체계 / 네이밍 정리

## 목적
현재의 `reliability score`는 사용자에게 **사람 자체의 신뢰도 평가**처럼 들릴 수 있다.  
로직보다도 **표현 방식**이 위험하다.

## 변경 권장
| 현재 | 권장 |
|---|---|
| reliability score | profile confidence |
| reliability | evidence alignment |
| 신뢰도 낮음 | 근거 부족 |
| 불일치 | 자기평가와 경험 데이터 차이 |

## 점수 표시 방식 권장
숫자보다 **상태형 표현**이 안전하다.

| 상태 | 의미 |
|---|---|
| 높음 | 자기평가와 경험 데이터가 잘 맞음 |
| 보통 | 일부 일치 |
| 낮음 | 아직 근거 데이터가 부족함 |

## 추가 권장 사항
- projectCount 0이면 일괄 감쇄하는 규칙은 유지하되 사용자에게 직접 드러내지 않기
- “낮음” 상태를 부정적으로 표현하지 말고 **데이터 부족**으로 안내하기

## 완료 기준
- 사용자에게 상처를 줄 수 있는 표현 제거
- 점수가 사람 평가가 아니라 데이터 일치도처럼 느껴진다
- 팀장도 오해 없이 해석할 수 있다

---

# 5. 파일럿용 이벤트 로깅 / 분석 체계

## 목적
이제부터는 기능 추가만큼 **실제 사용자 데이터 수집**이 중요하다.  
어디서 이탈하는지, 무엇이 쓰이는지 모르면 빠르게 개선할 수 없다.

## 꼭 남겨야 할 이벤트
| 카테고리 | 이벤트 |
|---|---|
| 인증 | login_started, login_success, login_failed |
| 팀 생성 | team_created, invite_link_copied, join_success |
| 설문 | survey_started, section_completed, survey_submitted |
| 결과 | result_viewed, role_recommendation_clicked |
| 팀 대시보드 | dashboard_viewed, reminder_sent, role_confirmed |
| 회의 허브 | meeting_created, ai_summary_generated, action_item_completed |

## 최소 분석 질문
- 설문 시작 → 완료율은 몇 %인가
- 설문 어느 섹션에서 가장 많이 멈추는가
- 결과 페이지에서 다음 단계로 이어지는가
- 팀장은 역할 제안을 실제로 확정하는가
- 회의 허브는 주간 재방문을 만들고 있는가

## 구현 방향
- 처음에는 DB 로그 테이블로 충분
- 추후 PostHog / Amplitude로 확장 가능

## 완료 기준
- 퍼널 분석이 가능하다
- 주요 이탈 지점을 확인할 수 있다
- 파일럿 5~10팀만으로도 개선 방향을 판단할 수 있다

# 6. GitHub 보강 품질 안정화

## 목적
GitHub 데이터는 객관적으로 보이기 때문에, 잘못 반영되면 오히려 왜곡이 커진다.  
따라서 “연결했다”보다 “어떻게 해석하느냐”가 중요하다.

## 위험 요소
- fork repo가 많아 실제 실력보다 과대/과소평가
- 오래된 계정이라 repo 수만 많음
- 언어 통계가 템플릿 repo 때문에 왜곡
- private repo 활동은 안 보임

## 우선 정리해야 할 것
| 항목 | 보정 방향 |
|---|---|
| repo 수 | 전체 수보다 최근 활동 repo 중심 |
| 언어 통계 | 최근 기여 기준 반영 |
| commit frequency | 최근 6개월 기준 제한 |
| 미연결 사용자 | 불이익 최소화 |

## 완료 기준
- GitHub 연결 여부가 과도한 불이익이 되지 않는다
- 오래된 / noisy 데이터가 추천을 망치지 않는다
- GitHub 보강 결과를 설명할 수 있다

# 7. Observer 경험 정교화

## 목적
Observer는 장기적으로 교수, 멘토, 운영자, 평가자 같은 buyer가 될 가능성이 높다.  
따라서 단순 읽기 전용이 아니라 **가치가 보이는 읽기 전용**이어야 한다.

## 추가하면 좋은 것
| 기능 | 설명 |
|---|---|
| Observer 전용 요약 카드 | 팀 강점, 보강 필요, 설문 완료율 |
| 개인정보 차단 강화 | 개별 점수, 이력서, 설문 원문 숨김 |
| 진행 단계 요약 | 준비 중 / 역할 정리 중 / 실행 중 |
| 회의 요약 전용 뷰 | 원문 없이 핵심 논의와 액션만 표시 |

## 완료 기준
- Observer가 제품 가치를 1분 안에 이해한다
- 학생 감시 툴처럼 느껴지지 않는다
- 기관 buyer에게 보여주기 좋은 화면이 된다

# 8. Direction tracker 최소 버전

## 목적
Meeting hub 다음 단계로, “계획대로 가고 있나?”를 보여주는 최소 운영 지표를 만든다.

## 왜 지금은 최소 버전만 해야 하나
Direction tracker는 데이터가 쌓여야 의미가 있다.  
회의 데이터와 GitHub 데이터가 충분하지 않으면 고급 분석은 empty state만 많아진다.

## 최소 구현 범위
| 기능 | 최소 구현 |
|---|---|
| baseline | 킥오프 목표 수동 입력 |
| actual | meeting action item 완료율 기반 |
| 시각화 | 간단한 진행률 바 |
| 경고 | on-track / behind 정도만 |

## 나중으로 미뤄도 되는 것
- confidence score
- GitHub webhook 기반 정교한 drift
- 원인 추론
- scope reallocation 제안

## 완료 기준
- 팀이 계획 대비 현재 상태를 한눈에 볼 수 있다
- 회의 허브 데이터와 연결된다
- 최소한의 운영 감각이 생긴다

# 한 줄 결론

**Kakao를 제외하면, 가장 먼저 해야 할 것은 `Meeting hub 최소 버전`이고, 그 다음은 `팀 대시보드를 실제 행동 허브로 바꾸는 것`이다.**  
즉, 이제부터는 **가입과 설문을 더 다듬는 것보다, 다시 돌아오게 만드는 루프를 붙이는 일**이 훨씬 중요하다.
